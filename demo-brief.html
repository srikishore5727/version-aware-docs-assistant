Every answer has a source.

VADA is a documentation assistant for the Nimbus API. A developer asks a question in plain English and gets a short answer where every claim links to the exact page, section, and product version it came from — or the product says it doesn't know.

01

What we built, in one minute

One search box. Type a developer question. Read a short answer. Click any citation number to jump to the passage behind it. That's the whole product.

For the developer

Stop guessing which doc applies

The answer names the version it came from, so nobody copies a v2 field name into a v3 integration. If the docs don't cover the question, it says so instead of inventing an endpoint.

For the business

Support answers that can be audited

Every response is traceable. That turns "the assistant told me" into "here is the page it cited", which is the difference between a demo and something a support team would trust.

For the docs team

Evidence of what is missing

When the product says "not found", it is a signal that a topic is unindexed or missing. Feedback buttons and request logs give the docs team a queue of gaps rather than anecdotes.

The one rule the whole system is built around

No answer without a citation. Not as a prompt instruction we hope the model follows — as a check in code that rejects the response if any citation does not match a retrieved passage.

02

The problem we started with

The vendor ships API references, migration guides, and changelogs for v1, v2, and v3 at the same time. Three tools already exist, and each fails in its own way.

Ctrl+F

Finds words, not questions

Ask "why do I keep seeing the same records on the next page" and the docs page says "duplicate records across pages". Almost no words match, so search returns nothing useful.

Generic chatbot

Answers confidently, cites nothing

It will invent a parameter name that looks plausible. For an API integration, a wrong field name is a production bug — worse than no answer at all.

Reading the docs

Version drift

The v2 page still exists, still ranks in search, and still gets copied. Nothing tells the reader that it was superseded six months ago.

So the design goal was three things at once: find by meaning (so paraphrases work), respect exact terms (so user_name and 422 still hit), and prove every claim (so a wrong answer cannot slip through).

03

How it works

This is a RAG system — Retrieval-Augmented Generation. In plain words: find the right pages first, then let the language model write an answer using only those pages.

01Split 12 docs cut by heading into 60 chunks, each tagged with version, type, section, URL.
02Index twice Words go into SQLite FTS5. Meaning goes into Chroma as 768-number vectors.
03Retrieve Both searches run, results are fused by rank, the best 5 survive.
04Answer The model sees only those 5 passages and must cite each sentence.
05Verify Code checks every citation, then renders the answer with linked sources.

Why two indexes

  • Keyword (BM25) is unbeatable for exact identifiers: user_name, 429, page_size.
  • Embeddings are unbeatable for paraphrases: "same records again" ≈ "duplicate records".
  • Fusion means each covers the other's blind spot, and keyword search is still there if the embedding service is down.

Why the answer can be trusted

  • Citations are parsed in code. A number that doesn't map to a retrieved passage rejects the whole answer.
  • One retry, then refusal. Still uncited? The API returns not_found, not prose.
  • Confidence is computed from the cited sources, never written by the model.
  • Superseded notices are computed from citation metadata, so the model cannot hide them.
The exact pipeline, for the technical questions

POST /api/ask → normalise filters → hybrid_search() runs FTS5 (BM25, title and section boosts) and Chroma (cosine, Gemini gemini-embedding-001, 768 dimensions, L2-normalised), fuses with Reciprocal Rank Fusion (K = 60), applies the relevance floor (0.60, calibrated embeddings only) and the superseded penalty (0.0015), returns 5 chunks → generate_answer() builds the numbered context, calls gemini-3.1-flash-lite, parses [n] and grouped [1, 3] citations, retries once with a corrective prompt, then either returns a cited answer, the extractive fallback, or not_found. Results are cached in process, keyed by question, filters, limit, and index mtime.

How it was built

The stack is deliberately small: one language, one web framework, one embedded database, one vector store, and no build step in the browser.

LanguagePython 3.10One language for ingestion, retrieval, evaluation, and the API.

Keyword indexSQLite FTS5 (BM25)Built into Python's standard library. No server to run, exact-term ranking for free.
VectorsChroma (persistent, cosine)Runs in-process on disk, so no vector database service to operate.
EmbeddingsGemini gemini-embedding-001768 dimensions, strong on technical text, one API key for both models.
GenerationGemini gemini-3.1-flash-liteFast and cheap enough for interactive use; the GA endpoint after the preview began returning 503s.
FrontendHTML, CSS, one JS fileNo framework, no build, no dependency tree. It is a document with a search box.

DesignBrand guidelines + design systemColours, type, radii, and motion are tokens; 12 tests fail if the UI drifts from the brand files.

Project rules we kept

  • PRD first. Requirements and a RAG architecture doc were approved before code.
  • One feature per PR. 20 build days, 20 feature PRs, each squash-merged.
  • CI on every PR. Tests plus the evaluation gate, so quality could not silently regress.
  • Docs follow the code. PROJECT_MEMORY.md is updated every day as a handoff.

What "done" meant

  • A question produces an answer with validated citations.
  • An out-of-scope question produces no answer.
  • A retired version is flagged, not hidden.
  • The build fails if retrieval quality drops.
  • The UI passes the brand and accessibility tests.

What recall@5 and MRR mean

  • recall@5 (1.00) — for all 30 test questions, the correct passage appears in the top five results, every time.
  • MRR (0.91) — on average the correct passage is near the top; 0.91 means it is usually first.
  • Why it matters — the answer can only be as good as the passages handed to the model, so retrieval is measured separately, with no model in the loop.

What CI actually checks

  • 186 tests — retrieval, citations, filters, confidence, cache, feedback, refresh, accessibility, brand tokens, theme.
  • Evaluation gate — 30 golden questions; the build fails below recall 0.85.
  • Hermetic — no API key, no network, so a green build is reproducible and free.

If something goes wrong

  • Model 503 or timeout: the answer still appears as a verbatim quote, labelled low confidence. Say so — it is the fallback working.
  • No network: switch to the offline path (VADA_EMBEDDINGS=hash) or show the saved screenshots.
  • Server won't start: check port 8000, then python -m app.refresh to rebuild the index.
  • A question returns not found: that may be correct. Ask a second, clearly in-scope one.

Three questions to have ready

  • Paraphrase: "Why do I keep seeing the same records on the next page?" — shows meaning search.
  • Exact term: "Which field replaced user_name in v3?" — shows precision and citations.
  • Out of scope: "How do I bake sourdough bread?" — shows the refusal.
08

Likely questions, answered

Open each one for the short answer and the depth behind it.

Why not just use ChatGPT with the docs attached?

You can, and that is roughly what this is — except the constraint is enforced, not requested. The model only sees the five retrieved passages, every citation is validated in code, and the confidence and version warnings are computed outside the model. A generic chat window gives you prose; this gives you prose plus evidence you can check.

How do you stop it hallucinating?

In layers. The prompt restricts it to numbered context. The code rejects any citation that doesn't map to a retrieved passage, with one retry. The relevance floor stops weak matches from being used at all. And superseded warnings are derived from metadata, so the model can't omit them. It can still choose the wrong passage — that is why the citation is one click away.

Why two search systems instead of one?

Keyword search is precise but literal; embeddings are flexible but blur exact identifiers. Fusing them by rank means each covers the other's weakness, and keyword search remains a working fallback if the embedding provider is unavailable.

How do you know retrieval is good?

A 30-question golden set scored without a model: recall@5 is 1.00 and MRR is 0.91. CI reruns it on every pull request and fails below 0.85, so a regression cannot merge silently.

What happens if the model is down?

The request degrades to a verbatim quote of the best retrieved passage, labelled low confidence, with its citation intact. The API never returns an uncited answer. If the embedding provider is down too, search falls back to keyword mode and says so in the response.

Why SQLite and Chroma instead of a "real" database?

The corpus is small and the deployment is one process. FTS5 ships with Python; Chroma runs on disk. That removes two services to operate and keeps the whole thing runnable on a laptop. The retrieval interface is small enough to swap either one later.

What does it cost to run?

One embedding call per query, one small generation call per answer, and nothing at all when the answer is cached. The test suite and CI cost nothing because they run offline with a local embedding stub and no model call.

How does it scale?

Today: a single process, in-process cache, and an index built offline. For real traffic the next steps are a multi-worker cache, a hosted vector store, and a background ingestion pipeline. None of that changes the answer contract, which is the part that matters.

What did you personally build?

Everything in the repository: requirements, architecture, the six Python modules, the UI, the evaluation harness, the CI pipeline, the tests, and the documentation. The project was delivered one feature per pull request, with each PR reviewed against acceptance criteria and merged only when CI was green.

What would you do with two more weeks?

Real documentation instead of the sample corpus, answer-level evaluation (not just retrieval), streaming responses, and conversation context. Those are the four gaps a real support team would feel first.

09

Limits, stated plainly

Naming what is not built is part of the deliverable. It shows the boundary was chosen, not missed.

Sample corpus, not production docs

Twelve documents across three versions, written for the exercise. The ingestion and citation contract stay the same with a real corpus; the content does not.

Retrieval is measured, answers are not

The golden set scores whether the right passage is found. It does not score whether the prose is the best possible answer — that needs human review or a judge model.

Single process

The answer cache and metrics are in memory. Running multiple workers needs a shared cache and a metrics backend first.

No auth, no memory, no streaming

Deliberate v1 exclusions from the PRD: internal tool, one question at a time, complete answers rather than token-by-token.

One model provider

Gemini for embeddings and generation. The interfaces allow a swap, but only one provider is wired and tested.

English, text only

No multilingual tuning, no PDFs, no images, no code execution. Markdown with front-matter is the only input format.

Jargon decoder

For your own recall in the room. Use the left-hand word, keep the right-hand explanation in your head.

TermPlain meaning
RAGRetrieval-Augmented Generation: find relevant pages first, then let the model write using only those pages.
ChunkA small section of a document — here, split by heading, about 500 characters, with a little overlap.
EmbeddingA list of numbers representing meaning. Similar meanings produce similar numbers, which is how paraphrases are found.
Vector storeA database that finds the nearest embeddings quickly. We use Chroma, stored on disk.
Cosine similarityThe distance measure between two embeddings: 1.0 is identical direction, lower is less related.
BM25The standard keyword-ranking formula: rare words count more, and documents where the word appears often rank higher.
FTS5SQLite's built-in full-text search module. No server, no extra dependency.
RRFReciprocal Rank Fusion: merge two ranked lists by position, not raw score. Ours uses K = 60 to keep the top ranks from dominating.
GroundingConstraining the model to the supplied passages, so answers are based on evidence rather than training memory.
HallucinationA confident answer that is not supported by any source. The failure mode this product is built to prevent.
CitationThe [n] marker in an answer, mapped by code to a retrieved passage and shown as a source card.
SupersededAn old version that still exists but should not be used for new work. Demoted in ranking and flagged in the answer.
ConfidenceA derived label (high/medium/low) from the cited sources: how many agree, whether they share a version, whether any are retired.
Relevance floorA minimum similarity (0.60) below which a passage is not considered evidence, so out-of-scope questions return nothing.
Extractive fallbackWhen the model is unavailable, quote the best passage verbatim with its citation instead of returning nothing.
Cache (LRU)Keeps recent answers in memory; the least recently used is dropped when full. Invalidated when the index changes.
recall@5Of all test questions, how many had the correct passage in the top five results. Ours is 1.00.
MRRMean Reciprocal Rank: 1.0 means the correct passage is always first. Ours is 0.91.
CIContinuous Integration: every pull request runs the tests and the evaluation gate automatically.
Squash mergeAll commits from a feature branch become one commit on main, so history reads as one feature per line.

How to make the review land

Six habits that separate a good demo from a good review. They are cheap and they are what a marker or a manager actually remembers.

1

Open with the user, not the stack. "Nimbus ships three versions at once" is a problem the room can feel. "I used FastAPI and Chroma" is a list. Stack comes at minute seven.

2

One claim, one proof. Every time you say "it's reliable" or "it's fast", point at the thing that proves it — a citation, a test count, a CI gate. Unproven claims sound like marketing.

3

Show the failure path on purpose. The sourdough question and the superseded notice are the strongest moments in the demo, because they show judgement rather than capability.

4

Name the trade-offs. Why two indexes, why Chroma, why no reranker, why no chat memory. A decision with a reason is engineering; a decision without one is a tutorial.

5

Own the bugs. Truncated answers, grouped citations, white-on-white dropdowns, the 503 model. Each one is evidence that the thing was tested and improved.

6

Close on the guarantee. "Every answer traceable, or an explicit refusal" is one sentence, it is true, and it is the reason the project exists.

Opening, 30 seconds

"A vendor keeps three versions of its API live at once. Developers lose time finding the right page and ship bugs when they use the wrong one. VADA answers the question and proves the answer, or says it doesn't know. I built it over twenty days, one feature per pull request."

Closing, 30 seconds

"The deliverable isn't a search box. It's a guarantee: no answer without a source. 186 tests, recall of 1.00 on a 30-question benchmark, and a CI gate that fails if retrieval gets worse. The next step is a real documentation corpus."

Things that cost marks

Don't

  • Read the features list as a list.
  • Say "the AI does it" without saying what is checked in code.
  • Hide the limitations until asked.
  • Apologise for the sample corpus — explain the boundary instead.

Do

  • Let the screen do the talking; narrate what changed, not what is on it.
  • Pause after the not-found demo. It is the strongest beat.
  • Use the PR numbers when you talk about process.
  • Finish early. Questions are where the mark is won.
